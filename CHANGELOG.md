# Changelog

All notable changes to this project are documented here.
Format based on [Keep a Changelog](https://keepachangelog.com/). This project uses date-based entries.

## [Unreleased] — 2026-07-17

Context-aware persona pass: the app now reveals group-leader, intercessor, learner, multilingual, privacy and pastoral capabilities **from existing behaviour** — no persona picker, no new navigation tab, and Grace's Today/first-prayer journeys unchanged.

### Rich updates & testimonies — 2026-07-20/21

Updates and testimonies can now carry more than plain text — formatting, photos, voice notes, video and links — without weakening the encryption story: **every media file is encrypted on-device before upload, always**, even when the owning row itself is legacy plaintext.

- **Markdown-lite writing** — `**bold**`, `*italic*`, `- ` bullet lists and auto-linked http(s) URLs render in updates, testimonies, prayer notes and descriptions (`src/components/rich/RichText.jsx`). The renderer builds React elements directly — never `dangerouslySetInnerHTML` — so user content cannot inject markup, and plain text renders unchanged, keeping every existing update readable with no migration. Clamped card previews flatten markers away (`plainText`) instead of showing `**Urgent**` as noise. A small selection-aware toolbar (`FormatToolbar` + `useMarkdownFormatting`) wraps the selection and restores focus/cursor after the re-render, shared by the update composer and the prayer-note field.
- **Attachments** — the new `UpdateComposer` attaches photos, voice notes, video files and links to personal and community updates and testimonies. Photos are downscaled to ≤1920px/JPEG before the size check (keeping whichever is smaller, GIFs passed through so animation survives); caps are 10 MB images / 20 MB audio / 50 MB video. Each file is encrypted with its **own AES-GCM key** (`mediaCrypto.js`) and uploaded to a **private `attachments` bucket** as `application/octet-stream` — the bucket never stores readable media, so its members-wide read policy leaks nothing. The per-file key travels in the row's attachment metadata, which lives **inside the E2EE payload whenever the row is encrypted** (the visible `attachments` column is redacted to `[]`); playback decrypts to a cached object URL per attachment. Links are normalized/validated (`https://` default, must have a real host) and open with `rel="noopener noreferrer"`.
- **Voice notes that iOS can actually hear** — recording asks for AAC as an **explicit codec** (`audio/mp4;codecs=mp4a.40.2`): given bare `audio/mp4`, Chromium records **Opus into the mp4 container**, and iOS Safari then shows a player that plays pure silence. Bare mp4 is trusted only where the browser cannot put Opus in mp4 (Safari), and webm/opus stays the last resort. The picker was extracted to `src/components/rich/recorderMime.js` and pinned by tests.
- **Authors can take content back, piece by piece** — a posted update or testimony now offers **Remove** on each attachment and on its text (author-only, always behind a ConfirmDialog), and the whole row is deleted once the last piece is removed, so no author+date shell lingers. Removals work through the offline mutation queue like every other write. On the server, `supabase/attachment_management.sql` adds the previously missing **author-only UPDATE policies** on `community_updates`/`testimonies` (admins still moderate by deleting whole rows — they could not re-encrypt someone else's E2EE payload anyway) plus **mirror-aware RPCs** (`sync_remove_update_attachment` / `sync_remove_update_text` / `sync_delete_update`) that shrink a plaintext personal update AND its fanned-out community mirrors in one call; E2EE rows never fan out and are rewritten client-side. Storage cleanup is best-effort — orphaned ciphertext without its key is noise.
- **Headers had to learn about media** — the CSP now allows `img-src blob:` and `media-src 'self' blob:` (decrypted media is served from object URLs) and Permissions-Policy grants `microphone=(self)` for voice notes (`vercel.json` + the dev-server headers in `vite.config.js`). Because the precached `index.html` is served **with the response headers captured at precache time**, an installed PWA that stays alive for days would keep enforcing the stale policy long after a deploy changed it — exactly how phones kept blocking blob: media after the fix shipped — so `main.jsx` now re-checks for a new service worker **hourly**.
- **Migrations** — `supabase/rich_media_updates.sql` (the `attachments` jsonb columns, the private bucket + policies, and `sync_add_update` learning attachments — dropping the old 5-arg overload first to avoid the PGRST203 trap) and `supabase/attachment_management.sql` (edit policies + removal RPCs, run after the first). **Run `rich_media_updates.sql` before deploying the client**: an update carrying media calls the 6-arg RPC and writes the `attachments` column, which an unmigrated database rejects — and the offline queue classifies that as permanent. Plain-text updates omit the new argument and stay compatible either way.
- **i18n** — 20 new keys × 16 languages (AI-authored, pending native review).
- **Tests** — +54 focused tests across this and the two passes below (808 total, all green): renderer safety and marker parsing, toolbar text math, composer attach/record/remove flows, the recorder-mime ladder per browser capability profile, media encrypt/decrypt round-trips, attachment and text removal incl. the delete-when-empty rule and offline executors.

### Honest series status & catch-up — 2026-07-20

- **A finished series stops calling itself "Active".** A recurring schedule whose end date has passed or whose occurrence count is consumed now reads **"Series ended"** (muted, not accent) on Journal cards and in the Prayer Detail schedule summary (`scheduleEnded` in `src/lib/planner.js`). One-time prayers are excluded on purpose — a past 'once' date often stays a live request; only a configured series end means "this plan is finished". The prayer itself stays in the journal, and answered still wins over ended.
- **A finished guided plan releases its card.** Plan cards were considered "running" whenever an active prayer referenced them, so a completed 7-day journey could never be started again without deleting the prayer. `runningPlanIds` now counts only runs whose series can still occur.
- **Catch-up stops asking about prayers already prayed.** A missed day is now considered caught up if the prayer was completed on that day **or any later day** — praying a request from its detail page today clears yesterday's miss instead of leaving a stale "missed" nudge (`catchUpPrayers`).

### Calm scheduling — 2026-07-19

Scheduling was already complete; it was just asked for all at once. This pass makes it **optional, understandable and progressive** without removing a single capability — the recurrence engine (`src/lib/schedule.js`), the planner and the persisted `prayers.schedule` shape are untouched, and no migration ships with it.

- **One question, three answers.** Opening the scheduler now asks *"When would you like this prayer to appear?"* with three full-width rows: **Use my normal prayer rhythm** (the existing plan-following `null` schedule), **Pray once**, and **Choose another rhythm**. The plan-following option no longer asks anyone to remember their weekly plan — it *shows* the days it really produces, resolved by the same planner Today uses (new `planWeekDays`, which honours the per-prayer weekday override, then the categories' plan, then the uncategorized every-day fallback). The date input, the rhythm rows and everything below appear only after the choice they belong to.
- **The common rhythms first.** "Choose another rhythm" offers **Every day / Once a week / Choose days**. Every-N-days, monthly and yearly are no less valid, just far rarer, so they moved behind **"More scheduling options"** — which opens by itself when the prayer already uses one, so reopening a monthly prayer never hides its own answer. Both sets are one radio group: the same single choice, not a second scheduling model.
- **Preferred time and the ending rule fold away, but never hide their value.** Each is a compact row that states its current answer (`Preferred time · Anytime`, `When should this rhythm stop? · No automatic end`) and reveals its choices on demand. Picking a time collapses the list again — *only for a pointer*, since arrow keys move the selection through a radio group and folding it away would strand a keyboard user mid-travel. Ending choices are stated in plain language ("When I mark it answered", "No automatic end").
- **A sentence, not a spec.** The confirmation reads *"This prayer will appear every Tuesday and Friday, at any time, until you mark it answered."* — rendered from the very schedule that will be saved. `scheduleSummary` (chips) and the new `scheduleSentence` share one field-by-field switch, so the preview and the stored object cannot drift apart; day names come from the locale (`Intl`), lists from `Intl.ListFormat`, and clauses are joined with the language's own separator (Arabic ، Japanese 、) via a `sentJoin` key rather than a hard-coded comma. Russian, Portuguese and Arabic use a parenthetical weekly form, because their weekday names carry a gender the quantifier would have to agree with.
- **Scheduling stays out of the prayer's way.** The new-prayer form shows one line — **Prayer rhythm · Every Tue · Anytime · Change**, plus "You can change this later." — inside the existing *Organize* disclosure. The chip row is gone. **A prayer still saves without any scheduling decision**, keeping the bounded weekly default exactly as it was (weekly on the day it was written, open-ended — deliberately *not* re-defaulted, since it is a protected default and its stored `end` is not ours to rewrite). A rhythm newly chosen *in the editor* does get the prayer-friendly `end: { kind: 'answered' }`, and an ending that was stored or explicitly picked is never replaced. On Prayer Detail, scheduling stays in the ⋯ overflow, its primary action is now the specific **"Use this rhythm"**, and closing it hands focus back to the ⋯ trigger.
- **Nothing existing moves.** Daily, weekly, interval, monthly, yearly and one-time schedules round-trip through `draftFromSchedule` → `scheduleFromDraft` byte-for-byte (asserted for all six). A saved multi-day week reopens on "Choose days", a single-day week on "Once a week", legacy `null` schedules stay `null` when saved untouched, and Cancel discards the draft on both surfaces while a save commits exactly once through the existing update path (so offline writes stay optimistic and replay unchanged).
- **Controls.** Full-width rows replaced the small pills: real `<input type="radio">` in named `<fieldset>`s (arrow keys, Space, group names for free), selection shown by a filled dot and a heavier border rather than colour alone, ≥44px everywhere, weekday buttons exactly 44×44 that wrap instead of shrinking, labelled date/number inputs, `aria-expanded`/`aria-controls` on every disclosure, and an `aria-live` confirmation. Enter inside a scheduling field no longer submits the surrounding prayer form.
- **Note on scope.** "Use my normal prayer rhythm" is now selectable for *new* prayers too (the spec asks for the three choices unconditionally). It is never the default and never preselected — the bounded weekly default still is — but this is a deliberate change from the previous rule that hid the plan-following mode from new prayers entirely.
- **Tests** — +46 focused tests (754 total, all green): progressive disclosure at each layer, what every choice persists, existing schedules reopening on the right row, round-trips, the sentence matching the draft, plan-following days, single-commit/Cancel-discards on both hosts, focus return, radio semantics and the form-submit guard.
- **i18n** — 37 new keys × 16 languages (AI-authored, pending native review).

### Final refinement pass — 2026-07-18

A last sharpening of the work above. No new personas, destinations or feature surfaces; Grace's onboarding and Today are untouched.

- **A plaintext prayer can no longer be shown as encrypted.** `protectionOf` previously inferred encryption from the *device vault* being unlocked, so a legacy plaintext row was relabelled "Encrypted" the moment a key existed. It now reads the prayer's OWN stored data — `encryption_version`, an encrypted payload, or the explicit marker the store records at write time — and takes no vault argument at all, so lock state cannot change a prayer's classification in either direction. Unlocking is a *read* capability: it opens ciphertext, it does not retroactively encrypt anything. Creation and confirmation are now distinct too: the form states the intent (**"Will be encrypted"**, from `plannedProtection`), while the saved confirmation states the fact, computed from the actual created prayer — or, if the store row hasn't landed yet, from explicit optimistic metadata passed by the caller rather than from global vault state (no `protectionOf({})` placeholder anywhere). An encrypted row that can't be opened here reads **"Encrypted · locked here"** instead of implying it is readable. Audience and protection stay separate labels with non-overlapping key namespaces.
- **Source language is correctable in context.** `content_language` still defaults from the active language — nobody is asked to pick one — but bilingual writers now get one quiet line, **"Written in English · Change"**, inside the *existing* Organize disclosure (and once in the community request form). The picker itself stays folded behind "Change" (`aria-expanded`/`aria-controls`, native `<button>` + `<select>`, ≥44px), so the default form gains a line of text and no new section. Explicit choices always beat the heuristic; a confident heuristic disagreement *offers* its reading as a tappable suggestion and never overwrites silently. Language ids are normalized to the supported set (`normalizeContentLang`: `en-GB` → `en`, unknown → null), legacy rows keep the heuristic fallback, and corrections survive edit, share, saving a community request personally, and offline replay. Scripture is still excluded from AI translation.
- **Prayer Detail has one clear hierarchy.** Pray now leads; **Add update** and **Mark answered** sit directly beneath it (side by side, stacking below 380px so long translated labels truncate instead of overflowing). Mark answered now appears **exactly once** — it opens the answered flow as a disclosure that carries its own Cancel/Confirm, replacing the second competing button that used to sit at the bottom of the page; the confirmation step is preserved and there is only one copy of the completion logic (the follow-up banner opens the same disclosure). Answered prayers show only Resume. Schedule, Follow-up, Scripture, Pin, Share, Edit and Delete stay in the ⋯ overflow, and `SchedulePlanner` is still never permanently expanded.
- **The group checklist tells the truth about what's available.** With no requests in the group the third row now reads **"Add a request first"** and opens the Add-request flow, instead of offering a "Begin praying" that cannot be honoured (`blocked` on the step, so the wording and the action agree). Opening a request's detail page still does not complete the step — only a confirmed prayer action does. The **Invite** step now completes when another member joins *without* the leader leaving and reopening the group: the card re-checks membership when the app returns to the foreground (`focus`/`visibilitychange`), which is event-driven rather than polled — no timer, one cheap request, and the listener detaches entirely once the step is done, so a live group and Low data mode cost nothing. Opening the members modal still completes nothing; copy/share/QR still do.
- **Accessibility.** The saved-confirmation close control is a real 44×44 button (the circle became decoration); the group invite **QR** control gained an accessible name, a 44×44 target and disclosure semantics; Prayer Detail's back, overflow, update-submit, remove-point and remove-verse controls carry accessible names rather than tooltips alone (and the hover-revealed ones now also reveal on keyboard focus). Toasts became a polite `role="status"` live region — saved/copied/completed are announced without interrupting — as did the offline banner, and the toast dismiss button is localized and 44px. A global `:focus-visible` outline replaces per-component rings that inline styles could defeat. The default overflow-menu trigger grew from 36px to 44px.
- **Migration/release.** `supabase/content_language.sql` verified against the real schema: all six tables exist, every column is nullable with no default, no RLS policy or column-level GRANT is affected, and nothing is backfilled. Documented the **required release order — run the SQL *before* deploying the client** — because a 400 from a missing column is classified permanent by the offline queue and the mutation would be dropped; the reverse order is safe. A verification query ships in the file. **This migration has not been applied to production by this change** (it needs Supabase credentials) — it remains a manual release step.
- **Tests** — +48 focused tests (696 total, all green): protection accuracy across both vault states and at the store/label/UI layers, creation-intent vs. confirmed-fact, source-language default/correction/normalization/precedence/propagation, Prayer Detail hierarchy and single-Mark-answered, checklist request-first wording and member-join completion (including "does not poll" and "detaches when done"), and the touched surfaces' names, targets, disclosure semantics, focus return, RTL and long-label behaviour.
- **i18n** — 7 new keys × 16 languages (AI-authored, pending native review).

The Privacy & Security section itself now opens as a compact list of disclosure rows (Privacy Center, Vault, Notification privacy, Low data mode, AI data use, Export) with Delete account kept apart at the bottom; generic notification previews remain the default.

### Security
- AI proxy (`/api/anthropic`) now **requires a valid Supabase session**; the Anthropic key is server-only (`ANTHROPIC_API_KEY`) and never shipped to the browser.
- Group joins are validated **server-side by invite code** (RLS no longer lets a user self-add by group id).
- Community prayers can only link a `source_prayer_id` the inserter owns (closes a tampering path through the sync RPCs).
- **End-to-end encryption ("Prayer Vault")** — private prayer content (title, description, person, phone, updates, prayer points, and now **testimonies**) is encrypted client-side and stored as ciphertext the server cannot read.
